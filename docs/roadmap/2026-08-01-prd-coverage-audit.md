### 1. `product_image` 入口是空壳

`POST /api/content-plans` 接受 `source: "product_image"`，但服务层没有任何图像理解，
只是把传进来的字符串当一句话用。结果是：商家上传产品图 → 拿到一份和图无关的计划，
而界面上没有任何迹象说明它没看图。

**这比不做更糟** —— 不做至少是诚实的。PRD §3 把「一张产品图」列为 P0 主入口之一。

修法：走 AI provider 的 `analyzeImages` 把产品图转成事实行，与商品链接抓到的事实同路。

### 2. 统一素材库没收纳图文帖与轮播

PRD §4.3 写的是「收纳上传原图、生成产品图、分镜、成片、**图文帖与轮播**、字幕/导出件」，
里程碑 M3 也明写「+ 统一素材库」。同行调研更把它列为 P0。

现状：`unified-library-service` 只有 order 与 batch 两个来源，`ContentPost` 完全没进去。
商家出完图之后，那些图只存在于「本周内容」页里，成品库里找不到。

### 3. R3 缺分组维度

PRD §4.3 R3：「按**钩子类型 / 模板 / 时长 / 画幅 / 植入档位**分组比较」。

现状只按 `recipeId`（= 钩子类型 + 形态）分组。时长、画幅、植入档位这三维虽然
已经作为快照列存在 `VideoJob` 上，但判定引擎读不到它们，
所以回答不了「9:16 是不是比 1:1 强」「自然植入是不是比角标强」。

决策 3（植入默认档从角标改自然植入）本来就需要这一维来验证换档有没有用。

### 4. O4 验收 2 与 3 未满足

PRD §3 O4 的四条验收标准：

| # | 验收 | 状态 |
|---|---|---|
| 1 | 拿到该行业**长期在投**广告的结构清单 | ✅ 按 daysRunning 排序与过滤 |
| 2 | 每条配方能说出「它为什么被判为有效」（已投天数、**迭代次数**等公开信号） | ✅ 已加 `variantCount` |
| 3 | 由配方生成的内容是原创的：**可通过重复度检查** | ✅ 字符 n-gram containment 检查，超阈值去掉参考重生成 |
| 4 | 系统内不保存、不再分发他人成片文件 | ✅ 表结构层面焊死 + 回归测试 |

第 3 条是合规主张的证据链：我们对外说「生成内容是原创的」，就得有一把尺子能证明。
